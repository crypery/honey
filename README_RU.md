# Honey

> [English version](README.md)

**Honey** - мультипротокольный ханипот, предназначенный для анализа внешних ботов, сканирующих, зондирующих и атакующих серверы. Он эмулирует несколько распространённых сетевых сервисов с реалистичными баннерами и сценариями входа, приманивает автоматизированные атакующие инструменты к взаимодействию с собой и незаметно фиксирует все попытки подбора учётных данных.

## Описание

Honey работает как единый бинарный файл на Go и одновременно слушает пять стандартных портов сервисов:

Все сервисы используют единое на-диске виртуальное файловое дерево с корнем `root/`. Каждый сервис <заперт> в подпути этого дерева (настраивается параметрами `*_path`):

| Сервис | Порт | Эмулируемая цель | Корень эмуляции (jailed) |
|--------|------|------------------|--------------------------|
| Telnet | 23   | Широкополосный роутер BCM96318 | шелл `root/` (`telnet_path=/`) |
| SSH    | 22   | dropbear 0.53.1 (встраиваемое устройство) | шелл `root/` (`ssh_path=/`) |
| HTTP   | 80   | Сайт WordPress 6.8.2 либо сервис Basic Authentication | сайт `root/home/public_html` (`http_path`) |
| HTTPS  | 443  | Сайт WordPress 6.8.2 либо сервис Basic Authentication | сайт `root/home/public_html` (`https_path`) |
| FTP    | 21   | Файловый сервер | файловый корень `root/home` (`ftp_path`) |

Каждый сервис может быть включён или выключен независимо через JSON-конфигурационный файл.

Эмулируемые цели намеренно подобраны так, чтобы походить на бесприсмотрные встраиваемые устройства (роутеры, шлюзы) и сайт WordPress по умолчанию - самые частые цели массовых сканирующих ботов. Когда внешний бот подключается и пытается пройти аутентификацию, Honey перехватывает полный набор учётных данных (логин и пароль), исходный IP-адрес и метку времени и записывает их в журнал по протоколу.

По умолчанию ханипот полностью пассивен: он никогда не выполняет команды атакующего и никогда не предоставляет доступ - каждое взаимодействие наблюдается, фиксируется и отклоняется. Опционально, для каждого сервиса отдельно, можно включить **режимы эмуляции**, предоставляющие *запертую* (jailed) сессию (ограниченный шелл или файловый корень, за пределы которого атакующий не может выйти), что приманивает интерактивных атакующих к выполнению команд, все из которых фиксируются. Оба режима безопасны для размещения на публичном IP-адресе.

## Особенности

- **Мультипротокольная эмуляция** - сервисы Telnet, SSH, HTTP, HTTPS и FTP работают одновременно в одном процессе.
- **Конфигурация сервисов** - каждый сервис включается или выключается независимо через JSON-конфигурационный файл, что позволяет выставлять только нужные сервисы.
- **Реалистичные баннеры** - SSH-сервис представляется как `SSH-2.0-dropbear_0.53.1`, а Telnet-сервис встречает клиента приветствием `BCM96318 Broadband Router`, имитируя типичное бесприсмотрное встраиваемое устройство и максимизируя число ботов, вступающих во взаимодействие.
- **HTTPS с TLS** - HTTPS-сервис работает по TLS с использованием локального сертификата (`localhost.crt` / `localhost.key`).
- **Эмуляция WordPress** - в режиме эмуляции HTTPS-сервис отдаёт полный статический снимок реального сайта WordPress 6.8.2: все страницы (главная, записи, архивы, страница входа), весь визуальный дизайн (тема, шрифты, стили, скрипты, изображения) и стандартные корневые эндпоинты (`index.php`, `readme.html`, `license.txt`, `wp-login.php`, `xmlrpc.php`, `wp-*.php`,...). Непознанные URL получают собственную стилизованную страницу 404 сайта. Каждый запрос фиксируется с меткой времени, исходным IP, HTTP-методом и URL, приманивая ботов и сканеры, нацеленные на CMS, раскрыть свои паттерны зондирования.
- **Перехват учётных данных** - каждая пара логин/пароль, попытка которой зафиксирована со стороны атакующего, перехватывается по всем протоколам (последовательность входа Telnet, парольная аутентификация SSH, заголовок HTTP/HTTPS Basic, вход в FTP).
- **Полный журнал аудита** - каждая перехваченная попытка записывается с меткой времени и исходным IP-адресом, отдельно по каждому протоколу, что позволяет сопоставлять активность одного бота по разным сервисам.
- **Пассивность или <запертая> сессия, по каждому сервису** - в режиме только перехвата команды не выполняются и доступ не предоставляется; в режиме эмуляции атакующий получает <запертый> шелл/файловый корень, строго ограниченный (обход путей отклоняется) и полностью логируемый, поэтому ханипот невозможно скомпрометировать через эмулируемые сервисы.
- **Единая виртуальная файловая система** - каждый сервис <заперт> в подпути единого на-диске дерева с корнем `root/`. <Запертые> шеллы Telnet/SSH накладывают на него реалистичную файловую систему встроенного Linux на базе busybox (роутер типа BCM96318): стандартные корневые каталоги, символьные ссылки на апплеты busybox, конфигурационные файлы `/etc` и псевдофайловые системы `/proc`/`/sys` эмулируются в памяти, а любой реальный файл, помещённый под `root/`, переопределяет эмулируемые данные по тому же пути. HTTP/HTTPS отдают `root/home/public_html`, а FTP - `root/home` из того же дерева.
- **Единый статический бинарник** - собирается с `CGO_ENABLED=0`, в результате получается самодостаточный исполняемый файл без зависимостей времени выполнения.
- **Кросс-компиляция** - одно исходное дерево собирается и для Linux, и для Windows.

## Технологии

- **Go 1.21+** - весь ханипот написан на Go и компилируется в единый статический бинарный файл.
- **golang.org/x/crypto/ssh** - реализация протокола SSH (обмен ключами, криптография, аутентификация), используемая SSH-ханипотом.
- **github.com/anmitsu/go-shlex** - разбиение строк команд SSH на слова в стиле shell.
- **Вендорные протокольные стеки** - серверные фреймворки Telnet, FTP и SSH закоммичены в репозиторий, поэтому проект собирается воспроизводимо с использованием лишь двух внешних модулей, перечисленных выше.

## Методика

1. **Развёртывание** - бинарный файл размещается на хосте с публичным IP-адресом и запускается с привилегиями, достаточными для привязки портов 21, 22, 23, 80 и 443. JSON-конфигурационный файл определяет, какие сервисы выставляются наружу.
2. **Приманка** - массовые сканирующие боты, сканеры портов и инструменты подбора учётных данных обнаруживают открытые порты и взаимодействуют с эмулируемыми сервисами так же, как с реальным бесприсмотрным устройством. Баннеры встраиваемых устройств (dropbear, роутер BCM96318) и снимок сайта WordPress специально привлекательны для случайных ботов: сканеры CMS исследуют установку WordPress в поисках страницы входа, админ-панели, стандартных корневых эндпоинтов и известных уязвимостей.
3. **Перехват** - каждая попытка аутентификации перехватывается на уровне протокола и фиксируется вместе с исходным IP-адресом и меткой времени. В режиме эмуляции WordPress каждый запрос (GET/POST и URL) фиксируется как журнал доступа. Неудачные входы отвечаются реалистичными отказами, чтобы бот продолжал своё поведение.
4. **Анализ** - собранные журналы позволяют изучать поведение ботов: какие списки учётных данных используются, какие инструменты и <отпечатки> клиентов встречаются, какие URL и эндпоинты исследуются, частота атак и сети-источники. Поскольку один и тот же бот обычно пробует несколько протоколов, журналы по протоколам можно сопоставить по IP и восстановить полную последовательность атаки бота.

Поскольку ханипот имитирует устройство низкой ценности и сайт WordPress по умолчанию, он привлекает большой объём случайного бот-трафика, что делает его эффективным сенсором для наблюдения за актуальным состоянием автоматизированных атак.

## Конфигурация

Все сервисы управляются JSON-конфигурационным файлом, читаемым при запуске. Каждый сервис может быть включён или выключен независимо:

| Параметр | Тип | Описание |
|----------|-----|----------|
| `telnet_use`  | bool | Включить сервис Telnet (порт 23). |
| `ssh_use`     | bool | Включить сервис SSH (порт 22). |
| `ftp_use`     | bool | Включить сервис FTP (порт 21). |
| `http_use`    | bool | Включить сервис HTTP (порт 80). |
| `https_use`   | bool | Включить сервис HTTPS (порт 443). |
| `http_emule`  | bool | Если `true`, HTTP-сервис отдаёт снимок WordPress из `http_path`; если `false`, требует аутентификацию HTTP Basic и перехватывает учётные данные. |
| `https_emule` | bool | Если `true`, HTTPS-сервис отдаёт снимок WordPress из `https_path`; если `false`, требует аутентификацию HTTP Basic и перехватывает учётные данные. |
| `ftp_emule`   | bool | Если `true`, FTP авторизует `emule_login`/`emule_pass` и отдаёт корень `ftp_path`; если `false`, каждый вход отклоняется (учётные данные всё равно перехватываются). |
| `telnet_emule`| bool | Если `true`, Telnet авторизует `emule_login`/`emule_pass` и открывает <запертый> шелл с корнем `telnet_path`; если `false`, каждый вход отклоняется (учётные данные всё равно перехватываются). |
| `ssh_emule`   | bool | Если `true`, SSH авторизует `emule_login`/`emule_pass` и открывает <запертый> шелл с корнем `ssh_path`; если `false`, каждый вход отклоняется (учётные данные всё равно перехватываются). |
| `telnet_path` | string | Подпуть единого дерева `root/`, используемый как корень <запертого> шелла Telnet. По умолчанию `/`. |
| `ssh_path`    | string | Подпуть единого дерева `root/`, используемый как корень <запертого> шелла SSH. По умолчанию `/`. |
| `http_path`   | string | Подпуть единого дерева `root/`, отдаваемый сервисом HTTP. По умолчанию `/home/public_html`. |
| `https_path`  | string | Подпуть единого дерева `root/`, отдаваемый сервисом HTTPS. По умолчанию `/home/public_html`. |
| `ftp_path`    | string | Подпуть единого дерева `root/`, отдаваемый сервисом FTP. По умолчанию `/home`. |
| `emule_login`  | string | Логин, принимаемый режимами эмуляции (Telnet, SSH, FTP, `wp-login.php` WordPress). По умолчанию `admin`. |
| `emule_pass`   | string | Пароль, принимаемый режимами эмуляции. По умолчанию `admin`. |
| `http_server`   | string | Значение заголовка `Server` для сервиса HTTP (порт 80). |
| `https_server`  | string | Значение заголовка `Server` для сервиса HTTPS (порт 443). |
| `ftp_server`    | string | Имя FTP-сервера, отправляемое в приветственном баннере `220`. |
| `telnet_server` | string | Telnet-баннер, показываемый клиенту при подключении. |
| `ssh_server`    | string | Строка версии SSH (баннер), объявляемая при рукопожатии. |

Если конфигурационный файл отсутствует, по умолчанию включаются все сервисы и все режимы эмуляции, а `emule_login`/`emule_pass` равны `admin`, а параметры `*_path` принимают значения `/` (Telnet, SSH), `/home/public_html` (HTTP, HTTPS) и `/home` (FTP).

### Режимы эмуляции

Когда режим эмуляции включён и атакующий вводит заданные `emule_login`/`emule_pass`, Honey предоставляет не отказ, а **<запертую> (jailed) эмуляцию**:

- **Telnet / SSH** - интерактивный шелл (`ls`, `cd`, `cat`, `pwd`, `whoami`, `id`, `uname`, `hostname`, `echo`, `clear`, `help`, `exit`), представляющий эмулированную файловую систему Linux на базе busybox (встраиваемый роутер типа BCM96318: апплеты busybox в `/bin`, конфигурация в `/etc`, псевдофайловые системы `/proc` и `/sys`, `/dev`, `/var`, `/root`, …). Эмулируемое дерево строится в памяти и накладывается на единый каталог `root/` (подпуть `telnet_path`/`ssh_path`, по умолчанию `/`); попытки выйти за его пределы (`cd../../etc`, …) отклоняются. Любой реальный файл или каталог, существующий под `root/`, переопределяет эмулируемые данные по тому же пути, поэтому оператор может положить реальные файлы (например, собственный `/etc/passwd` или `/var/log/messages`) в `root/`, чтобы точно контролировать, что видит атакующий. Каждая выполненная команда фиксируется в формате `метка_времени<TAB>ip<TAB>команда<TAB>полная_строка`.
- **FTP** - атакующий просматривает, скачивает (и загружает) файлы только внутри подпути `ftp_path` дерева `root/` (по умолчанию `/home`); обход путей (path traversal) блокируется.
- **WordPress** - отправка учётных данных на `wp-login.php` перенаправляет на фейковую админ-панель `wp-admin/`.

Когда режим эмуляции выключен, сервис всё равно перехватывает и фиксирует каждую попытку ввода учётных данных, но никогда не авторизует её. Это позволяет оператору вести полностью пассивный (только перехват) ханипот или полностью интерактивный (jailed) - по каждому сервису отдельно.

### Единая виртуальная файловая система

Все сервисы используют единое на-диске дерево с корнем `root/`. <Запертые> шеллы Telnet и SSH не показывают реальную файловую систему хоста: они накладывают на каталог `root/` виртуальную файловую систему (VFS), моделирующую минимальную встроенную Linux-систему на базе busybox - того типа, что встречается на роутере BCM96318. Эмулируемое дерево строится один раз, в памяти, при запуске и используется всеми сессиями:

- **`/bin`, `/sbin`, `/usr/bin`, `/usr/sbin`** - бинарник `busybox` и символьные ссылки на стандартные апплеты busybox (`ls`, `cat`, `ps`, `ifconfig`, `netstat`, `ping`, `grep`, `sed`, `awk`, …).
- **`/etc`** - конфигурационные файлы (`passwd`, `shadow`, `group`, `hosts`, `hostname`, `profile`, `inittab`, `init.d/`, `network/`, `dropbear/`, `ssh/`, `ssl/`, …).
- **`/proc`, `/sys`** - псевдофайловые системы (`cpuinfo`, `meminfo`, `net/`, `version`, …).
- **`/dev`, `/var`, `/root`, `/home`, `/tmp`, …`** - устройства, журналы и домашние каталоги.

То же дерево `root/` обслуживает и остальные сервисы: HTTP/HTTPS отдают `root/home/public_html` (снимок WordPress), а FTP - `root/home`.

То, что видит атакующий по Telnet/SSH, определяется двумя правилами:

1. **По умолчанию - эмуляция** - любой путь, существующий в VFS, показывается с эмулируемым содержимым, даже если такого файла на диске нет.
2. **Реальные файлы имеют приоритет** - если под `root/` существует реальный файл или каталог с тем же путём, его данные (содержимое, размер, права) переопределяют эмулируемую запись. Это позволяет оператору кастомизировать отдаваемые данные, просто положив реальные файлы в `root/`, не трогая эмулируемое дерево.

Поскольку VFS неизменяема и каждый сервис <заперт> в своём подпути `root/`, ханипот никогда не читает и не записывает за пределами этого дерева, и ни одна команда атакующего не может добраться до файловой системы хоста.

## Модули

| Модуль | Назначение |
|--------|------------|
| `golang.org/x/crypto/ssh` | Базовая реализация протокола SSH (обмен ключами, криптография, аутентификация), используемая SSH-ханипотом. |
| `github.com/anmitsu/go-shlex` | Разбиение строк команд SSH на слова в стиле shell для разбора. |
| `gliderlabs/ssh` (вендор) | Высокоуровневый SSH-серверный фреймворк: обработка сессий, обратные вызовы парольной аутентификации, TCP/IP-форвардинг, keep-alive. |
| `reiver/go-telnet` (вендор) | Telnet-сервер: согласование протокола, обработка соединений, опциональный TLS. |
| `reiver/go-telnet/telsh` (вендор) | Telnet-шелл-слой: запрос логина/пароля, регистрация и диспетчеризация команд. |
| `reiver/go-oi` (вендор) | Примитивы ввода-вывода (длинная запись, читаемые с перемоткой потоки), используемые Telnet-стеком. |
| `goftp` (вендор) | FTP-сервер: обработка команд, аутентификация, пассивные/активные data-соединения, а также файловый драйвер. |

## Сборка

Для обеих целевых платформ предоставлены скрипты сборки:

```bat
build_windows.bat:: собирает honey.exe (Windows amd64)
build_linux.bat:: собирает honey (Linux amd64)
```

Или вручную:

```
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w" -trimpath -o honey.exe.
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -ldflags="-s -w" -trimpath -o honey.
```
